## Вопрос 1. В чем разница между event.preventDefault() и event.stopPropagation()? В каких ситуациях используется каждый метод?
preventDefault() отменяет стандартное поведение браузера, связанное с событием: переход по ссылке, отправку формы, переключение чекбокса, показ контекстного меню. stopPropagation() останавливает распространение события по дереву DOM – обработчики на предках (при всплытии) или потомках (при захвате) не вызовутся. Это независимые вещи: можно отменить поведение, не мешая всплытию, и наоборот. preventDefault используют, когда поведение реализуется вручную (AJAX-отправка формы, SPA-навигация, кастомное контекстное меню). stopPropagation – когда событие не должно дойти до внешних обработчиков (вложенные кликабельные области, модальные окна, чтобы клик внутри не закрывал окно). Злоупотребление stopPropagation ломает делегирование, поэтому применять точечно.

## Вопрос 2. Как работает делегирование событий и какие преимущества оно дает по сравнению с назначением обработчиков на отдельные элементы?
Делегирование – назначение одного обработчика на общего предка вместо обработчика на каждом дочернем элементе. Событие от цели всплывает к контейнеру, где обработчик определяет источник через event.target.closest('селектор') и выполняет логику. Преимущества перед индивидуальными обработчиками: работает для динамически добавленных элементов без переназначения; меньше обработчиков – меньше памяти и накладных расходов; проще добавлять/удалять элементы (не нужно снимать обработчики); единое место логики – легче поддерживать и отлаживать; меньше утечек при удалении элементов. Ограничения: не все события всплывают (focus/blur – использовать focusin/focusout), нужна аккуратная фильтрация target, чтобы не реагировать на вложенные элементы, и осторожность с stopPropagation внутри.

## Вопрос 3. Какие фазы жизненного цикла события существуют в JavaScript (capturing, target, bubbling) и как они влияют на порядок выполнения обработчиков?
Три фазы: capturing (захват) – событие идёт от window/document вниз по дереву к цели; target – событие достигает целевого элемента; bubbling (всплытие) – событие поднимается от цели вверх к document/window. По умолчанию addEventListener регистрирует обработчик на фазе всплытия; третий аргумент true (или {capture: true}) – на фазе захвата. Порядок: сначала срабатывают capture-обработчики от внешних к внутренним, затем обработчики на цели (в порядке регистрации), затем bubble-обработчики от внутренних к внешним. Понимание фаз важно для делегирования, для перехвата события до цели (capture) и для предотвращения нежелательной обработки. stopPropagation останавливает дальнейшие фазы.

## Вопрос 4. В чем разница между event.target и event.currentTarget? Когда следует использовать каждый из них?
event.target – элемент, на котором событие фактически произошло (источник, самая глубокая цель), он не меняется при всплытии. event.currentTarget – элемент, на котором в данный момент выполняется обработчик (тот, к которому привязан listener); при всплытии он меняется на каждом уровне. Использование: target – когда нужен реальный источник (делегирование: определить, по какому пункту кликнули, через target.closest), currentTarget – когда нужен элемент, к которому привязан обработчик (например, this внутри обычной функции-обработчика равен currentTarget). В делегировании сравнивают target и проверяют предков, а логику привязывают к currentTarget (контейнеру). Важно: к моменту асинхронного вызова currentTarget может стать null.

## Вопрос 5. Как создать и запустить кастомное событие? Какие параметры можно передать в конструктор CustomEvent?
Создание: const event = new CustomEvent('my-event', { detail: { id: 1 }, bubbles: true, cancelable: true, composed: false }); запуск: element.dispatchEvent(event). Параметры: type (имя события, первый аргумент), detail – любые данные, доступные в обработчике через event.detail; bubbles – будет ли событие всплывать (по умолчанию false); cancelable – можно ли отменить через preventDefault (по умолчанию false); composed – выйдет ли событие за пределы shadow DOM. Обработчик назначается через addEventListener('my-event', e => console.log(e.detail)). Кастомные события используют для компонентной коммуникации, уведомления о действиях виджетов, интеграции с внешними скриптами; для простых случаев можно new Event('name', { bubbles: true }) без данных.

## Вопрос 6. Что такое debounce и throttle? В каких практических ситуациях их применение наиболее эффективно?
Debounce откладывает выполнение функции до паузы после последнего события: пока события идут часто, функция не вызывается; вызывается один раз, когда события прекратились (или прошло заданное время с последнего). Throttle ограничивает частоту: функция выполняется не чаще одного раза за интервал, независимо от количества событий. Debounce эффективен, когда важно финальное состояние: поиск с автодополнением, валидация после окончания ввода, автосохранение черновика, обработка resize после остановки. Throttle – когда нужна регулярная реакция во время непрерывного события: scroll (подгрузка, параллакс), mousemove, drag, ограничение частоты запросов к API, обработка pointermove. Оба реализуются через замыкание с таймером (debounce сбрасывает таймер, throttle запоминает время последнего вызова); выбирать по смыслу: "после" – debounce, "во время, но не часто" – throttle.

## Вопрос 7. Какие методы существуют для удаления обработчиков событий и почему важно удалять ненужные обработчики?
Удаление: element.removeEventListener(type, handler, options) – требует той же ссылки на функцию и того же значения capture, что при добавлении; для обработчиков, назначенных через свойство (el.onclick = fn), – присвоить null (el.onclick = null); удалить элемент из DOM – обработчики на нём собираются сборщиком мусора, но обработчики на внешних элементах (window, document) остаются; AbortController через signal – addEventListener(..., { signal }) и controller.abort() снимает все связанные обработчики сразу. Важно удалять, чтобы не было утечек памяти (обработчик держит ссылки на DOM и замыкания), не выполнялась лишняя логика на уже удалённых компонентах, не было дублирования при повторной инициализации и конфликтов. Особенно критично для SPA, long-lived страниц, обработчиков на window/document, таймеров и подписок.

## Вопрос 8. Как обрабатывать ошибки загрузки ресурсов (изображений, скриптов) и какие события для этого используются?
Для изображений и других медиа – событие error на элементе: img.addEventListener('error', handler) или img.onerror; для успешной загрузки – load (и loadeddata для видео). Для скриптов – script.onerror (срабатывает при сетевой ошибке или ошибке выполнения при загрузке внешнего скрипта; не даёт деталей из-за безопасности), onload – успех; динамически созданный script позволяет обработать ошибку и сделать fallback (загрузить другой CDN). Для link/stylesheet – onerror на элементе link. Глобально – window.addEventListener('error', ...) для ошибок выполнения и ошибок загрузки ресурсов (с capture: true для ресурсов), window.addEventListener('unhandledrejection') для промисов. Практика: fallback-изображение/источник, повторная загрузка, скрытие битых элементов, логирование; для изображений – также атрибут onerror или проверка naturalWidth.

## Вопрос 9. В чем разница между addEventListener и прямым назначением обработчиков через onclick, onkeydown и т.д.?
addEventListener позволяет повесить несколько обработчиков на одно событие, не перезаписывая предыдущие; поддерживает фазу захвата (третий аргумент), опции once, passive, signal; обработчики можно удалить через removeEventListener по ссылке. Прямое назначение (el.onclick = fn) хранит только один обработчик: новое присваивание затирает предыдущее, удаление – el.onclick = null; нельзя задать capture/passive/once; в обработчике this – элемент, event – первый аргумент. Прямые свойства короче и удобны для простых случаев, но плохо сочетаются с библиотеками и несколькими подписчиками. Современная практика – addEventListener, особенно для компонентов, делегирования и управления жизненным циклом; прямые обработчики допустимы в простом коде и для inline-разметки (но inline-обработчики смешивают разметку и логику и затрудняют CSP).

## Вопрос 10. Как оптимизировать производительность при работе с большим количеством событий? Какие лучшие практики существуют?
Делегирование – один обработчик на контейнер вместо тысяч; меньше памяти и подписок. Ограничение частоты – debounce/throttle для scroll, resize, mousemove, input; requestAnimationFrame для визуальных обновлений. passive: true для scroll/touch/wheel, чтобы не блокировать прокрутку; once: true для одноразовых обработчиков. Удаление ненужных обработчиков (removeEventListener, AbortController), особенно на window/document и при удалении компонентов. Не вешать обработчики на каждый элемент в больших списках – использовать виртуализацию и делегирование. Кэшировать ссылки на элементы, избегать тяжёлых вычислений в обработчике (выносить в Web Workers), не читать layout в цикле (layout thrashing). Использовать capture только при необходимости, не злоупотреблять stopPropagation, следить за утечками через замыкания и WeakMap/WeakRef при необходимости. Профилировать через Performance/Event Listener панели DevTools.

## Вопрос 1. В чем разница между Fetch API и XMLHttpRequest? Какие преимущества предоставляет Fetch API?
Fetch API – это современный интерфейс для сетевых запросов, основанный на промисах, тогда как XMLHttpRequest (XHR) – более старый API с событийной моделью и колбэками. Fetch предоставляет более чистый и читаемый синтаксис: запрос возвращает промис, который разрешается объектом Response, а не требует ручной настройки onreadystatechange. Преимущества Fetch: нативная поддержка промисов и async/await, более простая обработка заголовков через объект Headers, поддержка Request/Response как объектов (удобно для Service Workers и кэширования), потоковое чтение тела ответа (response.body), возможность отмены через AbortController. XHR всё ещё полезен для отслеживания прогресса загрузки (upload/download progress events) и в очень старых окружениях, но в современной разработке Fetch является стандартом.

## Вопрос 2. Как обрабатываются ошибки в Fetch API и почему ответ с HTTP статусом 404 не вызывает reject промиса?
Fetch отклоняет промис (reject) только при сетевых ошибках: отсутствие соединения, DNS-ошибка, CORS-блокировка, прерванный запрос. HTTP-статусы 4xx и 5xx считаются успешно завершёнными с точки зрения сети – сервер ответил, поэтому промис разрешается (resolve) объектом Response, у которого response.ok равно false (для статусов вне диапазона 200–299), а response.status содержит код. Это отличается от XHR, где 404 вызывал бы событие error. Поэтому после fetch необходимо явно проверять response.ok и при необходимости выбрасывать ошибку вручную: if (!response.ok) throw new Error(`HTTP ${response.status}`). Такой подход даёт больше контроля: можно обработать тело ответа с ошибкой (например, JSON с деталями) до выброса исключения.

## Вопрос 3. Какие методы HTTP поддерживает Fetch API и в каких случаях используется каждый из них?
Fetch поддерживает все стандартные HTTP-методы через опцию method: GET (получение данных, по умолчанию, без тела), POST (создание ресурса, тело с данными), PUT (полная замена ресурса, тело обязательно), PATCH (частичное обновление ресурса, тело с изменяемыми полями), DELETE (удаление ресурса, тело обычно отсутствует), HEAD (получение только заголовков без тела, для проверки существования), OPTIONS (получение поддерживаемых методов и CORS preflight). Реже используются TRACE и CONNECT. Выбор метода определяется семантикой: GET и HEAD безопасны и идемпотентны, PUT и DELETE идемпотентны, POST и PATCH – нет. Для REST API: GET – чтение, POST – создание, PUT – замена целиком, PATCH – частичное обновление, DELETE – удаление.

## Вопрос 4. Как работать с заголовками запроса и ответа в Fetch API? Приведите примеры полезных заголовков.
Заголовки запроса передаются в опции headers объекта init: либо как простой объект, либо как экземпляр Headers для более тонкого контроля . Пример: fetch(url, { headers: { 'Content-Type': 'application/json', 'Authorization': 'Bearer token' } }). Заголовки ответа доступны через response.headers (объект Headers) с методами get(), has(), forEach() . Полезные заголовки запроса: Content-Type (формат тела: application/json, application/x-www-form-urlencoded, multipart/form-data), Accept (ожидаемый формат ответа), Authorization (токен авторизации), Accept-Language, Cache-Control (no-cache для обхода кэша). Заголовки ответа: Content-Type (реальный формат), Cache-Control (политика кэширования), ETag (версия ресурса для условных запросов), Location (при редиректах), Set-Cookie. Важно: некоторые заголовки запрещены для установки из JavaScript (например, Host, Content-Length) по соображениям безопасности .

## Вопрос 5. В чем разница между PUT и PATCH запросами и когда следует использовать каждый метод?
PUT заменяет ресурс целиком: клиент отправляет полное представление ресурса, и сервер полностью перезаписывает существующие данные. Если какое-то поле не передано в PUT, оно обычно удаляется или сбрасывается. PUT идемпотентен: повторный запрос с теми же данными даёт тот же результат. PATCH применяет частичное обновление: передаются только изменяемые поля, остальные остаются нетронутыми. PATCH не обязан быть идемпотентным (хотя может). Использование: PUT – когда нужно заменить весь объект (например, обновление профиля целиком, сохранение формы со всеми полями); PATCH – когда нужно изменить одно-два поля (например, смена статуса заказа, обновление только email), это экономит трафик и снижает риск случайной перезаписи. В REST API PATCH часто реализуют через JSON Merge Patch или JSON Patch.

## Вопрос 6. Как реализовать авторизацию в Fetch API (Basic Auth, Bearer Token, OAuth2)?
Basic Auth: заголовок Authorization: Basic <base64(username:password)>. В браузере btoa кодирует строку, но это небезопасно без HTTPS и обычно используется только для внутренних API или при обмене кода на токен на сервере . Bearer Token: заголовок Authorization: Bearer <access_token> – стандарт для OAuth2 и JWT . Токен получают при логине и хранят в памяти или httpOnly cookie (безопаснее, чем localStorage). OAuth2: в браузере используется Authorization Code Flow с PKCE (не Client Credentials, который требует client_secret и должен выполняться на сервере) . Access token передаётся в заголовке Authorization: Bearer, refresh token используется для обновления. Практика: обёртка над fetch, которая автоматически добавляет заголовок Authorization и обрабатывает 401 с попыткой refresh; токен читать динамически при каждом запросе, а не кэшировать статически .

## Вопрос 7. Какие способы отмены запросов существуют в Fetch API и когда их следует использовать?
Современный способ – AbortController: создаётся контроллер, его signal передаётся в опцию signal запроса; вызов controller.abort() прерывает запрос, промис отклоняется с DOMException name === 'AbortError' . Устаревший способ – AbortController также заменяет удалённый AbortableFetch. Отмена используется: при уходе пользователя со страницы или компонента (cleanup в React/Vue), при новом запросе вместо устаревшего (поиск с автодополнением – отменять предыдущий запрос), при таймаутах (комбинация AbortController и setTimeout), при отмене пользователем длительной операции. Также signal можно передавать в несколько запросов, чтобы отменить их группой. Важно обрабатывать AbortError отдельно, не логируя как реальную ошибку.

## Вопрос 8. Как работать с разными форматами данных (JSON, FormData, Blob, ArrayBuffer) в Fetch API?
JSON: для отправки – body: JSON.stringify(data) и заголовок Content-Type: application/json; для чтения – await response.json(). FormData: body: formData (объект FormData из формы или созданный вручную), заголовок Content-Type не устанавливать вручную – браузер сам добавит multipart/form-data с boundary. Blob: body может быть Blob (файл, изображение), ответ читается через await response.blob() – удобно для скачивания файлов. ArrayBuffer: await response.arrayBuffer() для бинарных данных (аудио, видео, произвольные байты); также есть response.body как ReadableStream для потоковой обработки больших ответов. Текст: await response.text() для plain text, HTML, CSV. URLSearchParams: body: new URLSearchParams({...}) с Content-Type: application/x-www-form-urlencoded для старых API. Выбор зависит от того, что ожидает сервер и что нужно сделать с ответом.

## Вопрос 9. Как оптимизировать производительность при работе с множественными запросами (параллельное выполнение, кэширование)?
Параллельное выполнение: использовать Promise.all для независимых запросов, когда нужны все результаты; Promise.allSettled – когда частичный успех допустим; избегать последовательных await в цикле, если запросы не зависят друг от друга. Ограничение конкурентности: пул воркеров или библиотеки вроде p-limit, чтобы не перегружать сеть и сервер при большом количестве запросов. Кэширование: HTTP-кэш через заголовки Cache-Control, ETag/If-None-Match; на уровне приложения – Map с TTL или библиотеки (React Query, SWR) с дедупликацией одновременных запросов и stale-while-revalidate. Дедупликация: кэшировать промис в полёте, чтобы повторный вызов с теми же параметрами не создавал новый запрос. Отмена устаревших запросов (AbortController) экономит ресурсы. Батчинг: объединение нескольких запросов в один (например, GraphQL или кастомный endpoint). Для больших ответов – пагинация и потоковое чтение.

## Вопрос 10. Какие лучшие практики существуют для работы с Fetch API в production приложениях?
Всегда проверять response.ok и явно обрабатывать HTTP-ошибки, не полагаясь только на catch. Использовать обёртку (fetch client) с базовым URL, таймаутом (AbortController + setTimeout), автоматическим добавлением Authorization, обработкой 401 с refresh и централизованным логированием ошибок. Устанавливать таймауты, чтобы запросы не висели бесконечно. Обрабатывать AbortError отдельно от реальных ошибок. Кэшировать где уместно (HTTP-заголовки, клиентский кэш) и инвалидировать при мутациях. Использовать credentials: 'include' только когда нужны cookies, и понимать CORS. Для чувствительных токенов предпочитать httpOnly cookies вместо localStorage. Валидировать и санитизировать данные с сервера. Обеспечивать fallback UI при ошибках и повторные попытки с backoff для идемпотентных запросов. Логировать ошибки с контекстом (URL, статус, request id), но не логировать токены и персональные данные. Тестировать сетевое поведение (mocks, MSW) и медленные сети.
